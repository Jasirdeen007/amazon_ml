# AGENTS.md — Amazon ML Challenge 2026
## Autonomous Implementation & Execution Context

**Purpose:** This file is the authoritative execution guide for an implementation agent working on the Amazon ML Challenge 2026 Business Entity Resolution task.

The agent must execute the project end-to-end: inspect the supplied data and official instructions, build a scalable candidate-generation system, train and validate a pairwise matching model, generate the required outputs, validate them, and leave a reproducible final submission package.

---

# 1. Mission

Build an efficient, high-quality Business Entity Resolution pipeline that:

1. Uses only the permitted challenge data/resources.
2. Treats Source 1 as the reference entity set.
3. Finds matching Source 2 and Source 3 records for each Source 1 entity.
4. Generates a compact `candidate_pairs.tsv`.
5. Trains a pairwise matching model on candidate pairs.
6. Produces `matching_results.tsv`.
7. Optimizes the final decision process for the competition's F0.5 metric.
8. Handles zero-match/singleton entities.
9. Generalizes to the unseen France test country.
10. Validates the complete submission against the official specification.
11. Preserves reproducibility: every important artifact must be generated by code.

The agent must prefer measured improvements over adding complexity.

---

# 2. Non-Negotiable Rules

## 2.1 Competition constraints

Follow the official challenge documentation exactly.

Do not use:

- external business/entity databases
- web lookups for entity enrichment
- geocoding APIs
- commercial entity-resolution services
- government database lookups
- external data augmentation
- any other prohibited external source

Use only resources explicitly permitted by the competition.

If the official documentation contradicts this file, the **official documentation takes precedence**. Record the discrepancy in `DECISIONS.md`.

## 2.2 Data integrity

Never modify raw input files.

Create derived data under appropriate working/output directories.

Preserve:

- original IDs
- source identity
- required fields
- provenance

Do not silently drop records.

## 2.3 No brute-force matching

Never implement all-pairs comparison across millions of records.

Candidate generation must scale.

The candidate-generation system must reduce the search space substantially while retaining true matches.

## 2.4 Candidate generation is a first-class deliverable

`candidate_pairs.tsv` is part of the final submission.

The candidate-generation approach and resulting candidate-set size are evaluated alongside the final matching score.

Therefore:

> Minimize candidates while preserving high blocking recall.

Do not optimize only the final classifier.

## 2.5 Reproducibility

Every transformation required to reproduce the solution must exist in code/configuration.

Do not rely on:

- manual notebook edits
- undocumented preprocessing
- one-off local files
- unexplained thresholds
- manually selected candidate pairs

A saved model alone is not sufficient.

# 9. Phase 3 — Candidate Generation / Blocking

This is a critical phase.

## Objective

For each Source 1 entity, generate a small candidate set from Source 2 and Source 3.

Conceptually:

```text
S1 entity
   ↓
blocking
   ↓
small candidate set
```

Do not perform full pairwise comparison.

## Multi-pass blocking

Implement multiple independent candidate-generation passes.

Candidate strategies should be tested incrementally:

1. exact normalized-name keys
2. country
3. address/PIN/ZIP/city keys
4. phonetic name keys
5. token-based name retrieval
6. sparse TF-IDF top-k retrieval
7. additional safe keys discovered during profiling

Do not blindly implement every method.

Measure each method.

## Candidate union

Prefer:

```text
candidate_set =
    union(pass_1, pass_2, pass_3, ...)
```

rather than requiring every rule simultaneously.

This protects blocking recall.

## Candidate budget

Track:

```text
candidate_count_per_S1
mean candidates
median candidates
p95 candidates
p99 candidates
maximum candidates
total candidate pairs
```

The objective is:

```text
high blocking recall
+
small candidate sets
```

not merely the smallest possible candidate count.

# 10. Blocking Recall — Mandatory Gate

Using training ground truth:

For every known true match:

```text
Did the true pair survive blocking?
```

Calculate:

```text
blocking_recall =
true_matches_present_in_candidates
/
total_true_matches
```

Also calculate recall by:

- country
- source pair
- singleton/non-singleton where meaningful
- match multiplicity
- blocking method

Do not proceed to extensive model development until blocking performance is understood.

If a blocking strategy has poor recall, diagnose why.

---

# 11. Candidate Pair Dataset

The candidate-pair dataset is the bridge between blocking and ML.

Each row represents:

```text
one Source 1 record
+
one candidate Source 2/3 record
```

Conceptually:

```text
source1_entity_id | candidate_entity_id
S1-1001           | S2-4832
S1-1001           | S2-9271
S1-1001           | S3-1821
...
```

The exact final schema must follow official submission instructions.

For training, attach a label:

```text
1 = true match
0 = non-match
```

using the supplied ground truth.

Do not treat every unobserved pair as a confirmed negative unless the ground-truth semantics justify that assumption. Document the negative-sampling/labeling logic.

---

# 12. Training Pair Construction

After candidate generation:

```text
candidate pairs
      ↓
join against ground truth
      ↓
positive / negative labels
      ↓
pairwise feature matrix
```

The training dataset is **not** the raw business dataset.

The ML training row is:

```text
Source 1 record
+
candidate record
+
similarity features
+
label
```

This is a pair-classification problem.

---

# 13. Negative Sampling

Because non-matching candidate pairs can greatly outnumber true matches:

1. Measure the positive/negative ratio.
2. Avoid creating an unnecessarily huge training matrix.
3. Preserve hard negatives.
4. Ensure negative sampling does not distort validation.

Useful hard negatives include:

- same country
- same city
- similar name
- similar address
- same PIN/ZIP
- high blocking similarity but incorrect entity

These are more useful than trivial unrelated records.

Document all sampling rules.

# 14. Phase 4 — Pairwise Feature Engineering

For every candidate pair, calculate features.

## Name features

Evaluate:

- normalized exact match
- character similarity
- Levenshtein similarity
- Jaccard similarity
- token overlap
- TF-IDF cosine similarity
- common substring/LCS-style feature
- phonetic equality/similarity

## Address features

Evaluate:

- normalized exact match
- token overlap
- Jaccard
- character similarity
- city similarity
- state similarity
- PIN/ZIP exact match
- house/building number match
- address numeric overlap

## Metadata

Potential features:

- country equality
- source-pair indicator
- missingness indicators
- candidate-generation method indicators

Do not include target leakage.

Do not use an ID as a predictive feature merely because it correlates with labels.

# 16. Phase 5 — Model Training

Start with **XGBoost or LightGBM**.

The model learns:

```text
similarity features
       ↓
match probability
```

It does not directly predict an entity ID.

Initial training:

```text
X = pairwise features
y = 0/1 match label
```

Use class weighting or controlled sampling where appropriate.

Do not optimize only training accuracy.

---

# 17. Train/Validation Split

Avoid leakage.

If the same Source 1 entity appears in both train and validation pairs, performance can become artificially optimistic.

Prefer grouping validation by Source 1 entity:

```text
all pairs belonging to S1-X
```

must remain in the same split.

Also inspect:

- country distribution
- singleton representation
- positive/negative balance

If a temporal structure is meaningful, evaluate a time-based split as an additional experiment.

---

# 18. Primary Metric

The competition uses F0.5.

Track:

- F0.5
- precision
- recall
- F1
- singleton/no-match performance
- per-country metrics
- per-source-pair metrics

F0.5 places more emphasis on precision.

Do not choose a default `0.5` probability threshold without validation.

# 20. Singleton / No-Match Logic

A Source 1 entity can have zero matches.

Therefore:

```text
best candidate probability < threshold
        ↓
NO MATCH
```

Do not force every Source 1 entity to match something.

Also evaluate candidate ranking ambiguity:

```text
best score
second-best score
score margin
```

A small margin may indicate an ambiguous case.

Test conservative rules only if validation demonstrates improvement.

# 22. Phase 7 — Error Analysis

Inspect:

## False positives

Ask:

- Are names too similar?
- Are common company names causing collisions?
- Is address evidence weak?
- Is the threshold too low?
- Is a blocking method producing misleading candidates?

## False negatives

Ask:

- Did blocking miss the true candidate?
- Did normalization fail?
- Did transliteration cause failure?
- Was the address incomplete?
- Did the classifier reject a valid candidate?

Separate:

```text
blocking failure
```

from:

```text
classifier failure
```

This distinction determines where engineering effort should go.

# 38. Core Principle

The implementation agent must continuously distinguish three different problems:

```text
1. BLOCKING
"Which records are worth comparing?"

2. MATCHING
"Are these two records the same business?"

3. SUBMISSION
"Is the final output exactly what the competition expects?"
```

A strong classifier cannot recover a true match that blocking discarded.

A strong blocker cannot compensate for a poor classifier.

A strong model is useless if the final submission is malformed.

Therefore the project must optimize the complete pipeline:

> **High blocking recall + very small candidate sets + strong pairwise classification + conservative F0.5-optimized decisions + exact submission compliance.**
